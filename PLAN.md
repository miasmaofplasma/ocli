# ocli — Plan

Living document: design decisions, remaining work, open questions. Update it as decisions land; the AI assistant maintains it alongside the code.

## Goals

1. Ship a CLI the owner uses daily for ticket tracking against their Obsidian vault.
2. Learn project-shaped Rust: module organization, error handling, serde, clap, integration testing — with standard crates, understanding what they do underneath.
3. Keep ocli specific-by-default but general in mechanism: conventions the owner's team controls (branch patterns, frontmatter types, section names, ignore lists, template) live in config, so convention drift is a config edit — never a rewrite of hard-coded decisions.

## Confirmed requirements

- Vault markdown files are the sole source of truth; no Obsidian API or app interaction.
- A ticket is `features/<KEY>-<ID>.md`; the ID is the filename. Listing = directory read.
- Ticket inference from the current git branch (`[A-Z]+-\d+` pattern); explicit `--ticket` flag overrides; repo identity inferred from git remote/folder and matched against the `repo` frontmatter field.
- Read anything, write only: owned frontmatter fields + CLI-owned `##` sections created on demand. Never touch user prose, wikilinks, or Meta Bind blocks.
- Status vocabulary: `Backlog`, `In Progress`, `In Review`, `Complete`, `Blocked`. `status: Complete` ⇔ `done: true` kept in sync.
- v1 command set: `new`, `list`, `status`, `note`, `questions`.

## Design decisions

| # | Decision | Rationale |
|---|---|---|
| D1 | Direct filesystem access, no Obsidian/HTTP layer | Vault is a plain folder of markdown; removes a whole dependency class; better learning surface (file IO, error handling) |
| D2 | CLI-owned `##` markdown sections; bold-paragraph pseudo-headings are read-only | `##` headings are trivially and reliably parseable anchors; existing notes keep their organic `**bold**` style, untouched |
| D3 | Standard crates: `clap` (derive), `serde` + a YAML crate for frontmatter, `regex`, `anyhow` (app errors) + `thiserror` (library-style errors) | Boring and idiomatic; each is a standard learning topic in itself |
| D4 | Ticket ID lives in the filename; frontmatter `aliases` carries it too | Matches the existing vault convention (BCP-74043.md aliases BCP-74043) |
| D5 | Frontmatter edits rewrite only owned fields; unknown fields preserved | Notes are shared with Meta Bind widgets (`relates-to`, `blocked-by`); clobbering them would be data loss |
| D6 | Integration tests run against a fixture vault copied to a temp dir | The real vault is user data; tests must be isolated and full-suite-safe |
| D7 | Config file lives in the standard location found via the `directories` crate (`ProjectDirs`); on Linux that is `~/.config/ocli/config.toml` | User decision at planning; XDG-conventional for config (the *data* dir, `~/.local/share/ocli/`, is reserved for future state — configs conventionally go in config_dir) |
| D8 | CLI-owned `##` sections insert before the trailing run of `#`-headings + fenced code blocks at EOF (e.g. before BCP-74043's `# Relates to` / meta-bind block); if no such trailing run, append at EOF | Keeps plugin widgets last where the user expects them; exact detection algorithm lands in Phase 4 |
| D9 | YAML crate: `yaml_serde` — the official YAML org's maintained fork of `serde_yaml` | Original `serde_yaml` is archived; `serde_yml` is unsound (RUSTSEC-2025-0068); `yaml_serde` is the maintained, API-compatible choice |
| D10 | Sync `std::fs` IO; no async runtime | File ops are microseconds on page-cached 50KB notes; nothing to overlap. `tokio::fs` is a threadpool wrapper around the same blocking calls. If a future network feature (e.g. Jira fetch) adds real waiting, revisit for that command only |
| D11 | Hybrid write path: updates to existing files are edit-operations applied surgically (read → parse with spans → apply edits → render with untouched regions byte-identical → re-read-and-retry if source changed → temp file in same dir → atomic `rename`); `ocli new` never rewrites existing files (see D12: it renders the template). Edit-as-operation makes optimistic retry lossless | `rename()` is POSIX's only atomic swap; full-byte write is unavoidable, byte-preservation is not. Surgical ops replay cleanly against concurrently-changed files; full re-serialize would clobber in-window Obsidian/Meta Bind changes. Bounded-retry optimistic concurrency |
| D12 | `ocli new` renders the user's QuickAdd template file (config field for template path, default `templates/Feature.md`) as the single source of note shape. ocli implements an explicit placeholder subset: `{{VALUE:X}}` filled from CLI args (`ocli new BCP-74043` → `FeatureType=BCP`, `TicketNumber=74043`; `--set X=Y` for extras) and `{{DATE:...}}`/`{{TIME:...}}`; Meta Bind widget text renders verbatim; any unrecognized construct (e.g. `<%...%>` Templater syntax) is a hard error naming the offending line | Identical notes from Obsidian and ocli is enforced by fail-loud subset rendering, not by emulating template engines; ocli generates no YAML — frontmatter, sections, and filename all derive from template text, so template edits can't fork the two creation paths |
| D13 | Repo identity = normalized `origin` remote name: read origin's URL via `gix` (D14), strip protocol/user and trailing `.git`, take last path segment (`git@host:org/connected-module-item-api.git` → `connected-module-item-api`). Fallback: git-root folder basename when no origin remote; `--repo` flag overrides both; hard error outside a git repo unless overridden. `new` fills the empty `repo:` line with the quoted `"[[<name>]]"` post-render — no existence check, unresolved wikilinks are fine in Obsidian. `list` filters to the current repo's tickets by default (identity match per this rule), `--all-repos` widens to the whole vault | Remote is the single intrinsic source: survives local folder renames, matches Jira/PR URL naming; folder name coincides by clone convention. Known edge: forked repos have origin = fork — use `--repo`. Folder basename kept as fallback, not primary |
| D14 | All git access via `gix` (gitoxide, pure Rust) — repo discovery, HEAD/branch, remote URL from config, revwalk for history. No `git` subprocesses, no C dependencies (rules out `git2`/libgit2). Trim transport features (ocli never touches the network). Pin the version; the facade crate is 0.x and breaking changes between minors are expected — the plumbing crates in use (`gix-ref`, `gix-config`, `gix-actor`, `gix-mailmap`, `gix-revwalk`) are the project's stabilization-candidate tier | Supersedes the earlier read-`.git`-files plan: hand-parsing history means a packfile parser (out of scope), and `git log` subprocesses mean text parsing per command. gix handles worktrees/submodules/mailmap/insteadOf correctly by construction and scales to future git features. Owner-inference changes: `--repo`/`--ticket` overrides unchanged |
| D15 | Owner inference for `new`: walk commits on `base..HEAD` (base = `origin/main`, fallback `main`) oldest non-merge first; author identity canonicalized via mailmap, matched against person notes' `email` ∪ `git-user` fields (person notes gain optional `git-user` list for alternate identities). Fill `owner: "[[notes/people/<Name>.md|<Name>]]"` (house format). Multi-author branches: still fill from the oldest commit's author, with a visible warning listing all authors. Empty owner when: no branch-only commits, detached HEAD, or unmapped author email (warning names the email). `--owner "<name>"` overrides everything via fuzzy alias lookup over person notes | The initiator is the best single proxy for ticket ownership; reflog "branch creator" was rejected — reflogs are machine-local and record the *fetcher* for fetched branches, i.e. the wrong person in exactly the "not my ticket" case |
| D16 | `ocli fm <field> <value>`: general frontmatter setter — surgical line edit (D11 machinery), replacing the field's line or inserting it if absent. `status` is a thin wrapper over the same edit function (adding vocabulary validation + `done:` sync). Guardrails: refuse managed fields (`status`/`done`/`Created`/`repo` — each has code-level rules; error names the owning command) and refuse any field on the config `ignore` list (D18). Value parsing/emission driven by the field's configured type (D18); empty value → `field:` empty, never removes the line | One general write primitive + thin sugar beats parallel special-case commands; both guardrail tiers keep ocli out of fields that have invariants or other owners |
| D17 | `new` fills `Created` from the branch's **first commit author date** (same `base..HEAD` walk as D15), rendered `YYYY-MM-DD HH:mm` local time. Fallback to *now* when the branch has no commits yet. ocli replaces the template-rendered `Created:` line post-render (same surgical fill as `repo`); overridable via `--set`/`fm` | Author date survives rebases (committer date does not) — reflects when work on the ticket actually started, not when the note was written. Accepted divergence: QuickAdd-created notes keep note-creation time |
| D18 | Config-driven frontmatter schema: a `[frontmatter]` table in the config file maps field name → type: `string` (default for undefined fields), `int`, `float`, `bool`, `olink`, `list<T>`. Emission rules per type: numbers/bools bare, strings quoted, `olink` always a quoted `[[name]]`-style link — bare names auto-wrapped, full `[[path|alias]]` accepted, `|` aliases legal, unbalanced brackets/newlines rejected. Validation on read and write per type; unknown type name or a config type on a managed field → config-load error (fail-loud, matching D12's philosophy). `[frontmatter] ignore = [...]` (default `["relates-to", "blocked-by"]`) lists fields ocli refuses to edit — owned by Obsidian/Meta Bind, modifiable without code changes. `list<T>` in the type system from day one; `fm` input syntax for lists is a v1.1 nicety | Instead of hard-coding field knowledge, the config describes how ocli treats fields — new/changed fields are config edits, not code changes. Closed type set (no user-defined types, no expressions) is the guardrail against schema-language scope creep. `olink` auto-wrap is the recorded default; say otherwise to require full `[[...]]` input |
| D19 | CLI-owned sections: names configurable via a `[sections]` config table — `progress`, `notes`, `decisions`, `questions` (defaults `Progress`, `Notes`, `Decisions`, `Open Questions`); heading level always `##` (D2). One append primitive + thin sugar commands (D16 pattern): `ocli progress`/`note`/`decision`/`question` append to their section, look-then-create (create per D8 if absent; the user's template pre-seeds all four). Entry formats: `- YYYY-MM-DD HH:mm — text` for Progress/Notes/Decisions; Questions use `- [ ] YYYY-MM-DD HH:mm — text` checkboxes — resolved by ticking in Obsidian, `ocli questions` filters to unchecked (`--all` widens). Semantics: Progress = completed-task log answering "where am I in this ticket"; Notes = scratch capture (random thoughts, proto-questions/tasks to hand-reorganize later in Obsidian — never scanned by `ocli questions`) | Separate sections mirror how existing notes already treat these concerns; checkboxes give "open question" a definition with zero extra state; scratch Notes stays unstructured by design — promotion to Decisions/Questions is a human act in Obsidian |
| D20 | Ticket-key extraction: `[tickets] branch_pattern = '^(?<FeatureType>[A-Z]+)-(?<TicketNumber>\d+)'` (configurable; TOML single-quoted to avoid escapes). Contract (as amended by D21): all capture groups must be named; compiled at config load; invalid regex → config-load error. Default is anchored (branch conventions put the key first); a non-anchored pattern is a deliberate loosening. Policy split: (a) commands that need a ticket (`status`, `fm`, `progress`, `note`, `decision`, `question`) with an unparseable branch or detached HEAD → error naming branch, pattern, and `--ticket`; (b) `new` REQUIRES the current branch to match the pattern → hard error on `main`/release/untracked-bugfix branches (branch-first workflow, prevents misfiled notes and keeps `jira` URL derivation unambiguous); (c) `new` argument key vs branch mismatch (including conflicting capture values, D21) → visible warning, proceed. ID argument is uppercase-normalized (`bcp-13423` → `BCP-13423`) and validated as `[A-Z0-9]+-\d+`; filename is always `<ID>.md` | Inference is a convenience, `--ticket` is the contract; hard-failing `new` off-ticket prevents the most expensive mistake class (misfiled notes) while warn-not-refuse on mismatch keeps legitimate pre-creation flows open |
| D21 | Branch regex uses **named** capture groups that feed the template value map: `branch_pattern = '^(?<FeatureType>[A-Z]+)-(?<TicketNumber>\d+)'`. Value map layers, merged by authority: `--set` flags > argument-derived values (the key `BCP-13423` splits into `FeatureType=BCP`, `TicketNumber=13423`) > branch named captures. Ticket ID remains argument-sourced (D20) — filename/alias/lookup unchanged; the pattern's job is convention verification (D20's hard check) plus contributing extra values. Edge rules: unnamed capture groups → config-load error; branch capture conflicting with argument-derived value → the D20c mismatch warning naming both; template placeholder missing from all layers → render-time hard error naming the placeholder | Unifies D12 (template substitution) and D20 (branch parsing) into one decomposition rule — the config describes how a branch name decomposes, exactly the convention-in-config-not-code move Goal 3 describes; removes the key-splitting special case instead of adding machinery. `regex` crate supports `(?<name>...)`; TOML literal strings keep patterns escape-free. If the ID ever stops being a simple join, a composition key can be added as a config edit |
| D22 | Config-defined template statics: `[template] path = "..."` (the D12 template path moves here) and `[template.values]` — scalar TOML values (strings verbatim, ints/floats/bools bare; arrays/tables → config-load error) that resolve `{{VALUE:Name}}` placeholders as a fourth value-map layer. Precedence: `--set` > argument-derived > branch named captures (D21) > `[template.values]`. Substitution stays **literal text** — the template author controls quoting (QuickAdd parity, D12); D18 read-side validation catches any YAML type weirdness. Built-ins `{{DATE:...}}`/`{{TIME:...}}` remain hardcoded grammar, not config | Completes the value-map story: standing defaults (config) vs context (branch) vs intent (`--set`); new template params are config entries, not code changes (Goal 3); literal insertion keeps ocli byte-compatible with QuickAdd rendering |

## Remaining work

Phased; each phase ends with something runnable.

- [ ] **Phase 0 — hygiene:** commit current scaffold, `.gitignore` (`/target`, `/.direnv/`), add deps: `yaml_serde` (D9), `directories` (D7), `toml` (D7/D18 config), `clap`, `regex`, `anyhow`, `thiserror`.
- [ ] **Phase 1 — config:** read vault root + `[frontmatter]` type table (D18) + `[sections]` names (D19) + `[tickets] branch_pattern` (D20) + `[template]` path and values (D22) from a TOML config file located via the `directories` crate (D7); `--vault` flag overrides. `ocli list` fails with a clear error when unresolved.
- [ ] **Phase 2 — read path:** frontmatter model (`serde` structs, optional fields, wikilinks as plain strings), `list` command with status filter. Fixture vault in `tests/`.
- [ ] **Phase 3 — create path:** `new` renders the QuickAdd template (D12) with the full value map (D21/D22), fills `repo` per D13 and `Created` per D17 (fallback `now()` until Phase 5 lands), writes atomically, refuses to overwrite. Branch-pattern hard check (D20b) activates in Phase 5 when gix lands — until then `new` requires the branch check to be skipped deliberately, flagged in help text as pre-Phase-5 behavior.
- [ ] **Phase 4 — write path:** `status` (frontmatter edit with round-trip fidelity, D5); append primitive + `progress`/`note`/`decision`/`question` commands (D19). Write machinery per D11: `Note::parse/apply/render`, atomic temp+rename, `new` refuses to overwrite existing files. Add `fm` general setter (D16) with type-driven emission (D18) once the edit machinery exists.
- [ ] **Phase 5 — git context:** via `gix` (D14) — branch matching + named-capture value map per D21, `--ticket` override; `status`/`fm`/`progress`/`note`/`decision`/`question` become ID-free; `list` repo-filtering per D13; owner inference per D15; `Created` switches to first-commit author date (D17).
- [ ] **Phase 6 — cross-ticket views:** `questions` aggregates unchecked entries from each note's configured questions section (D19) across `features/`; `--all` includes resolved.
- [ ] **Phase 7 — polish:** `clippy`/`fmt` clean, shell completions, help text.
